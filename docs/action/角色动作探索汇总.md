# 角色动作 · 探索汇总

> 为「角色技能修改」模块做的**数据摸底汇总**。
> 所有数字都是**实测**（数据源为游戏归档直出），推断与待查项**单独标注**，不与事实混排。
> 逐项细节与可重跑的生成脚本在 `gen/` 仓库，对照表见文末；本文可独立阅读。

---

## 0. 一句话结论

角色动作**不是一张表**，是三层：

| 层 | 内容 | 格式 |
|---|---|---|
| **动作表** | 每个动作的静态参数：制冷/充能、派生目标、调用哪些 motion、附带哪些 Buff | msgpack（`.msg`） |
| **时序轨 Flags** | 这条动作的**时间轴**：第几秒允许派生、开无敌、触发 Buff、调 FSM | Binary XML（`.bxm`） |
| **FSM** | 弹道/实体/AI 的节点图 | msgpack（`.msg`） |

三层**都是"改文件即落地"**，没有导出/转换步骤 —— 与武器、天赋树那条（DB → 点导出 → `.tbl`）是两条完全不同的路。

> **⚠️ 但"能改文件"≠"运行时都会读"。** 实测下来只有 **动作表** 与 **flags 轨** 完全可用；
> `_seq_edit_effect` 只能改"效果身份/大小"、**改不了时间**；`_seq_edit_attack` **运行时完全不读**。
> 完整能力边界见 **§8**。

而**它们一个字都不在 `.tbl` 里**：`system/table/` 下没有任何 action / flags / fsm 表（`skill.tbl`、`skill_status.tbl` 是**因子技能**，不是角色动作）。

## 1. 数据源与复现

游戏归档：`<游戏安装目录>\data.i`（本机为 `D:\Programs\Steam\steamapps\common\Granblue Fantasy Relink\`）
`data.i` 是索引（约 13 MB），内容在 `data.0` ~ `data.11`。

```powershell

    -i "<游戏>\data.i" -o "gen\extracted" -f system/player --overwrite   # 动作表

    -i "<游戏>\data.i" -o "gen\extracted" -f pl/pl1000     --overwrite   # 某角色的 motion + 时序轨
```

`gen/extracted/` 是既有的数据根（**已 gitignore**）。
**生成脚本与逐项记录不进本文档体系，在 `gen/probe/` 与 `gen/docs/`。**

## 3. 动作表 `*_action.msg`（实测）

| 项 | 实测值 |
|---|---|
| 文件 / 记录 | 36 个文件，**1429** 条记录 |
| 字段**并集** | **89** 个 |
| 单文件键数 | **不是固定 87** —— 有 **8 种**：`58 / 69 / 71 / 76 / 85 / 86 / 87 / 88`（玩家侧 85~88） |
| 文件内一致性 | 36/36 文件内部所有记录的键序列**完全一致** |
| 顶层 map | 键名**全部重复**为 `ActionInfo`（同一 map 里的同名键），一条 = 一个动作 |
| 非全集键 | **32 个**键不是每个文件都有；编号越大越稀有（`actionFreeWork28_` 只在 10/36 出现） |

### 格式事实

- **所有标量都是字符串**，包括数值（`"50"`）和布尔（`"true"` / `"false"`）。没有原生 int/bool。
- **空值有 4 种写法**，不能混为一谈：`-`（10300 次）、`-1`（8788）、`""`（4588）、`0`（62502）。同一字段内还会混用。
- 唯一的**非标量字段是 `supportEffectList_`**。

### `supportEffectList_` 结构（已证实）

```
[ 数量N, buffId1, p1..p6, buffId2, p1..p6, ... ]
```

- 数组长度只有 5 种：`1`(1225) / `8`(160) / `15`(29) / `22`(12) / `29`(3)
- `长度 = 1 + N×7` —— **零次不符**（步长 7 成立）
- Buff 数量分布：0 个 1225 条、1 个 160、2 个 29、3 个 12、4 个 3

## 4. 动作表的外键（实测）

| 字段 | 指向 | 验证结果 |
|---|---|---|
| `id_` / `branch*_` / `derivedId_` | **同文件内**其它动作 | ✅ **99.5%**（1588/1596 次引用命中；未命中仅 5 个值，都很小，疑似已删动作） |
| `abilityTag_` | `ability.tbl` → 翻译表 | ✅ **258/268**（见下） |
| `saveMotId01~12_` | `pl/plXXXX/` 的 motion 号 | ✅ **85%（炎帝）~100%（古兰等）**（见下） |
| `controlTypeHash_` / `supportTypeHash_` | 哈希词典 | ⬜ **尚未接** |
| `bulletType_` | FSM | ⬜ **尚未接** |
| `damageLimitDataIndex_` | `plXXXX.msg` 参数数组 | 本次不涉及 |

### 4.1 `abilityTag_` → 技能中文名

- 名字**来自游戏自己的翻译表**：`system/table/text/<语言>/text.msg` 里的 `TXT_AB_*`（中文 479 条，**只在这一个文件**，其他 50 多个分域 `text_*.msg` 一条都没有）
- 268 个 `abilityTag_` → 直接命中 242，**角色共享回退**再命中 16，合计 **258 / 268**
- **角色共享规则**：翻译表里**没有 `TXT_AB_PL0100_*`**（姬塔），而 `AB_PL0100_*` 有 16 个 → **姬塔与古兰（PL0000）共用技能名**，取 `TXT_AB_PL0000_*` 即全中
  （与「姬塔和古兰共享天赋树」是同一个游戏设计）
- 仍缺 10 个（`AB_NP0000_04`、`AB_PL2000_05`、`AB_PL2100_09..16`）—— **已查清不是解析问题**：
  1. `_CG` 变体解释了"16 vs 8"（8 个正名 + 8 个 `_CG`）
  2. 这些键在 `ability.tbl` 里**是真实行**（带 `ReqCharaId1` / `SkillType`）
  3. 但全语言全 `text_*.msg` 都搜不到显示名
  → **`ability.tbl` 行数多于"有名字的技能数"，多出来的是预留/未启用槽**。读取时应**回退显示键名**，不编造。

### 4.2 `saveMotId*_` → motion

值的**就是**文件名里那个 4 位十六进制 motion 号：

```
saveMotId01_ = "0000"  →  pl/pl1000/pl1000_0000.mot
                           pl/pl1000/pl1000_0000_0_seq_edit_flags.bxm
                           pl/pl1000/pl1000_0000_0_seq_edit_facialmotion.bxm …
```

**判据**：编号空间若无关，随机命中期望只有 ~2%（约 1300 个号 / 65536）；实测 85%~100%，故为同一编号空间。

一个 motion 号带出一整族文件：`mot` `flags` `facialmotion` `ik` `effect` `attack` `camera` `cloth` `se` `mesh` `eyecontrol` `speed` `vib`。

→ **动作表只管"参数与目标"；动作真正长什么样，要看它引用的这些 motion 文件。**

## 5. Flags 时序轨（实测，炎帝 222 条轨）

```xml
<SeqRoot><FlagsTrack SeqNum="N">
  <Seq LayerFlag="4294967295" StartTime="0.000000" EndTime="16.666668"
       Config="0" Flag0="8207" Flag1="0" SysFlag="0" FreeArg="0 0 0 0" />
</FlagsTrack></SeqRoot>
```

| 项 | 实测 |
|---|---|
| 规模 | 704 行 / 222 文件，平均 3.17 行；行数 1~17 |
| **时间单位** | **秒**，最小 `0.016667` = **1/60**（帧精度）；最大 33.02 |
| 属性 | **可选**：213 个文件有 `SysFlag`，9 个没有（与动作表"非全集键"同现象） |
| `FreeArg` | **恒为 `0 0 0 0`** → 保留字段 |
| `LayerFlag` | 几乎恒为 `0xFFFFFFFF`（701/704） |
| `Config` | `0`(497) / `1`(205) / **`32769`(2)** ← 有意外值，不是 0/1 枚举 |
| `SysFlag` | `0`(673) / `1`(20) / `4`(1) |
| `StartTime` 重复 | 同文件内 180 次 → **正常**（不同轨道可同时开始），不是数据错误 |
| Flag0 用过的位 | 26 个（常用值 `8206` / `8207` = bit1+2+3+13(+0)） |
| Flag1 用过的位 | 15 个（常用值 `4194304` = bit22、`1`、`131072` = bit17） |

⚠️ 位用量只是**炎帝一个角色**（全角色的那份见 §5.1）—— 某位没出现**不等于**游戏没用它。
⚠️ 位到"效果名"的对照表**游戏数据里没有**，需要自己逆（或用 `bxm` 之外的途径）。

### 5.1 全角色扫描（32 个角色、17,928 个 Flags 轨文件、30,545 行）

| 项 | 实测 |
|---|---|
| `Config` | `0`(20,101) / `1`(10,433) / **`32769`(11)** ← 仍不是 0/1 枚举，含义未知（见 §8.5） |
| `32769` 分布 | 卡塔莉娜 `pl0200`×6（`3203` 子轨 0/1/2、`3300` 子轨 0/1/2）、萝赛塔 `pl0600`×1、兰斯洛特 `pl0800`×1、巴恩 `pl0900`×1（各 `3300`）、珀西瓦尔 `pl1000`×2（`3302`、`3303`） |
| `32769` 的形态 | 11 处**全部是 1 帧**的段（`EndTime - StartTime = 0.016667`）且 `Flag0=65536`、`Flag1=0` |
| `Flag0` 用过的位 | **bit0 ~ bit31 全部出现过**（炎帝那份是 26 个位） |
| `Flag1` 用过的位 | bit0~10、bit12、bit13、bit15~20、bit22~24、bit26~31；**32 个角色都没出现过：bit11 / bit14 / bit21 / bit25** |

⚠️ Flag1 那 4 个"没出现过"的位只是**这批解包数据**里的结论（NPC / 未用到的 motion 可能覆盖不到），不等于游戏没用。

### 5.2 Flag0 / Flag1 的**取值**分布（同一批 30,545 行）

位用量之外，取值本身也扫了一遍 —— **多位组合是游戏数据里真实存在的**，不是谁把单位值拼出来的：

| 项 | Flag0 | Flag1 |
|---|---|---|
| 不同取值 | **133** 个 | **50** 个 |
| 单个位（0/1 位） | 32 个 | 28 个 |
| **多位组合（≥2 位）** | **101** 个 | 22 个 |
| 组合行数占比 | **24.7%** | 3.3% |
| 出现最多 | `0`(6504)、`32`(3227)、`4`(2616)、`1`(2103)、`16`(1588)、**`8206`(1205)**、**`8207`(1189)** | `0`(19970)、`4194304`(3631)、`1`(1003)、`256`(698)、`512`(612) |

- `8206` = bit1+bit2+bit3+bit13（允许连接动画 / 允许闪避 / 允许跳跃取消 / 允许释放技能）—— **数据里真有**，
  1205 次，是第 6 多的取值；`8207` 就是它再加 bit0（允许移动取消），1189 次。
- ⚠️ 曾经写进前端代码的那份 `FLAG0_VALUES` / `FLAG1_VALUES`（"观测清单"）**当时就不全**：Flag0 只记了 91 个
  （实测 133，少 42 个，其中 5 个还是单位值，如 bit12 = 4096）。那份清单已删 —— 界面现在按**位**算值
  （勾中的权相加），不需要取值快照。

扫法（可复现）：`pl\<角色>\<角色>_<motion>_<子轨>_seq_edit_flags.xml` 里 `Flag0="…" Flag1="…"` 逐对正则取值、
按值计数；位数用二进制串里 1 的个数数（**不能**用 JS 位运算，>2³¹ 会翻符号）。

**只以组合形式出现过的位**（在数据里从没单独成值）：

| | 单独成值出现过的位 | 只出现在组合里的位 |
|---|---|---|
| Flag0 | 29 位 | bit10 / bit29 / bit31 |
| Flag1 | 25 位 | bit11 / bit14 / bit15 / bit21 / bit25 / bit29 / bit31 |

这就是为什么界面的勾选列表必须**把 32 位全列出来**（位表里没名字的写 `bitN`）：只列"单独出现过的位"，
上面那几位在组合里就勾不动、也取消不掉 ✗。目前两张位表都发满 32 条（`FLAG0_NAMES` 有名字的 16 条、
`FLAG1_NAMES` 11 条，其余显示 `bitN` —— 位到效果名的对照表游戏数据里没有，见 §5）。

## 6. 与第三方工具的交叉验证

拿同一 motion、第三方工具产出的 `.xml` 与我们从游戏 `.bxm` **自己直转**的 `.xml` 逐字节比对：

> **222 / 222 完全相同**（炎帝全部 flags 轨）

两个结论：

1. 工具侧那份 xml **就是游戏原始数据**，不含作者改动（与「`pl/` 下游戏有 8346 个 flags，工具侧 8343 个」吻合）
2. 我们的解析路径与它**等价** → 不必依赖它

> 原则：名称/描述一律取自**游戏自己的表与翻译表**；第三方产物只用于交叉验证，不进管道。

## 8. 运行时能力边界（全部实测）

### 8.1 哪一层真正参与运行时

| 层 | 改值 | 加行 | 改时间 | 依据（实测现象） |
|---|---|---|---|---|
| **动作表** `*_action.msg` | ✅ | — | — | 给撕裂加力量的 `supportEffectList_` → **霸体图标出现** |
| **flags 轨** `_seq_edit_flags.bxm` | ✅ | ✅ | ✅ | 同上；`branchAtkHit_` 接招也被触发 |
| **effect 轨** `_seq_edit_effect.bxm` | ✅ `EffNo`/`Scale` | ❌ | ❌ | `EffNo 700→5220` → **出现力量特效**；`StartTime 0→0.7667` → **特效整个消失** |
| **attack 轨** `_seq_edit_attack.bxm` | ❌ | ❌ | ❌ | `AttackRate 3.9→39` + `Reaction 2→22` + `Size→20³`（时间不动）→ **毫无变化** |
| **FSM 挂载** `bulletType_` | ❌ | — | — | 见 8.2 |
| **`branchAtkHit_` 接招** | ✅ 能触发 | — | — | 但会产生**第二个动作**（带它自己的动画与僵直） |

> **补**：`.mot`（动画）里搜不到攻击/特效参数（`3.9` / `0.8` / `5.8` / `5200` / `700` 全都不在），
> 所以那些数据**只存在于独立轨文件里**；而 attack 轨运行时不被消费 —— 两者合起来即"力量的伤害搬不动"。
> 另：一次挥击可以有**多条同时刻判定**（撕裂 3 条时间戳相同 = 近/中/远三个判定盒），**条目数 ≠ 段数**。

### 8.2 FSM 层（已摸清；结论：炎帝挂不上）

- **每角色 FSM 绑定表**：`system/player/parameter/plXXXX/plXXXX_parameter.msg` → `fsmParam_`
  （两个平行数组 `folderName_[]` + `fsmName_[]`；pl1000 = `pl1000/snd_auto_base_1`、`pl_base/snd_auto_type_2`、`pl1000/snd_auto_unique_1`）
- **17 个角色**用了 `bulletType_`；其中 **12 个**可用 `bulletType_ - 1` 索引到自己的 `fsmName_`（1 基下标）
- 官方文档（Nenkai《Actions / Parameters》）原话：`bulletType_`「**只在特定角色上使用，值→FSM 的映射写在 exe 里**；FSM 由该动作 motion 里的 `Flag1:4` 调用」
- **炎帝不是"特定角色"**：全部动作 `bulletType_` 为空
- **实测（8 个文件已确认加载）**：`fsmParam_` 追加 `pl1000/cyclon` + 撕裂 `bulletType_=4` + flags 加调用位
  （含"两个位必须同一行 `Flag1=144`"的复测）→ **均无反应**
- → **"给任意动作挂任意 FSM"在数据层做不到。**

### 8.3 那炎帝的 FSM 是谁在调

- 赤焰旋涡的 motion `3470` 里有 `Flag1="144"`（= 128 + 16）→ 调 FSM
- `ab_atk_short_cyclon`（赤焰旋涡的 FSM）在 exe 里是**硬编码字符串**；`ab_atk_hit_bomb` **在 exe 里根本不存在**
- **同角色内逐字段对比**（撕裂 `id=4` vs 赤焰旋涡 `id=8`）：动作表里**没有任何"FSM 绑定"字段的差异**
  （差异全是数值：冷却/点数/距离/伤害上限/motion）
- → 炎帝的 FSM 调用是 **exe 内按技能硬编码**，不是数据驱动

### 8.4 参考工具（`refs/GBFRModToolV3.4`）的能力边界

它的全部接口（读 `app.js` 实测）：

```
/api/action/{char}/{id}  (+ /relations /save /restore)
/api/fsm/{char}/list 、/api/fsm/{char}/{name}  (+ /add_block /remove_block)
/api/player/{char}  (+ save/restore)  、/api/player/global/{damage,move,sparts}
/api/sigil_*  /api/buff_types  /api/fields  /api/load  /api/save  /api/tools/export-db-to-tbl
```

→ 它能编辑：**动作表字段 + flags 轨 + "已被调用的" FSM 内部（加/删 block）+ 角色参数**。
→ 它**不能**给一个动作"挂上"新 FSM —— 所以**它同样做不到"撕裂同时打出力量"**。
它比我们强的地方仅在于：对**本来就带 FSM 的角色/技能**，可以直接改 FSM 内部。
