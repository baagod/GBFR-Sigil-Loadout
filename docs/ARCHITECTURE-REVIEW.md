## 一、现状：四个可交付单元 + 一张没有主的数据网

四个单元的划分**不是历史偶然，是宿主逼出来的**：

| 单元 | 语言 | 拥有 | 不拥有 |
|---|---|---|---|
| Reloaded-II 托管壳 | C# | 生命周期、250ms tick、文件日志、全局热键、`loadout.json`→ABI 翻译，以及**并入的第二个特性**（因子参数编辑器，走 `IDataManager`） | 注入本身；因子的真值 |
| 原生核心 | C++ | 语义布局解析、2 个 hook + 2 处循环上限 patch、虚拟槽 `GemData` 合成、专属槽表、SEH 安全访问、授权记账、hot-apply | 玩家配置的形状；UI |
| 可视工具 | Go / Wails | 玩家配置的**唯一写者**、多语言名、单实例 / 托盘 / 假隐藏、"召唤 / 隐藏"的另一半 | 注入；游戏内状态 |
| 界面 | React | 作者界面 | 一切持久化 |

**不随包发布、但参与构建的**：`gen\`（仓库外：解包数据 + Go 生成器）、`refs\`、PowerShell 构建 / 部署。

**真正的问题在这张网上**：

| 事实 | 现在有几份形态 | 唯一拥有者 |
|---|---|---|
| 因子 / 技能表（203 行） | `Loadout\assets\gem.json`（随包文件）· `kCharacterExclusives[]`（C++ 编译表）· 可视工具内嵌的 `gem.lang.json` | **没有** |
| 专属表（29 行） | `gem.chara.json`（随包文件，只有可视工具读）· `kCharacterExclusives[]`（C++） | 同一生成器，却是两份产物 + `-Check` 门禁 |
| "载荷合法" | TS 夹 cap / 过滤 · Go 查结构 · C# 查 cap 与技能存在性 · 原生收 3 个位 | **没有** |
| 全局热键 | mod `RegisterHotKey`（只认游戏在前台）· 可视工具自己听同一个键隐藏自己 | **没有**（靠 `tool-hotkey.txt` 单向播报） |
| ABI | 4 处声明 | ✅ **有，而且治理得最好**：v19 + packing + 尺寸断言 + fail-closed |
| 跨语言常量（约 20 条） | 一张人工同步的文档表 | **没有** |

## 二、判定

**对的部分（别动）**

- 四个单元的划分是**宿主契约**逼出来的：Reloaded-II 要 .NET 程序集、注入要 C++、可视工具要在游戏之外有界面、界面用 Web。这条分层换来的是"每层只做它非做不可的事"。
- **ABI 是唯一被真正治理过的边界**（版本 + packing + 尺寸断言 + fail-closed）。这说明项目**有能力**把边界定好，只是只定好了一条。
- 两个特性共用一个宿主，而它们只共享 tick / 日志 / 用户目录 = **宿主 + 两个适配器**，不是耦合。可以接受。

**不够好的部分（只有一条，但它是根源）**

> **同一份事实被多个层各自持有，而没有任何一层被指定为它的唯一拥有者。**

这不是"代码乱"，是**所有权缺失**。它所有可观测的复杂度都从这一条长出来：

- 一份因子表存三遍 → 于是需要 `-Check` 门禁、87 行对拍、`assets\` 布局协调、mod 启动 fail-closed 门；
- 一份载荷合法性四层各写一半 → 于是"等级上界"有三份实现，而且 Go 那份校验的不是真正的不变量；
- 一个热键两个进程各自解释 → 于是需要 `tool-hotkey.txt` 这个反向通道；
- 20 个常量靠人工表 → 于是每次改动都要补一行。

**结论：当前组织"能用但未定"。先定归属，简化才有落点**——这正是"架构没定好，怎么简化还是在原地"。

## 三、目标架构：按"谁拥有事实"重新划缝

一句话：**每份事实只有一个拥有者；数据文件只有一份、可读可替换；跨层只剩两个半契约。**

> **修正（用户否决，2026-09-19）**：这里原写的是"发布物里**不放**数据文件"——**错的**。`Loadout\assets\`
> 是可见、可替换的数据源：内嵌（`go:embed`）会让可视工具的数据变死，新资产就得重编才能用，而"有新资产时
> 换一份 assets 配置照样能用"正是要保住的性质。要拆的是**重复的持有者与失败路径**，不是那个文件。

### 3.1 所有权表（目标）

| 事实 | 唯一拥有者 | 别人怎么用它 |
|---|---|---|
| 因子 / 技能 / 等级效果的真值 | **游戏** | 谁都不缓存 |
| 表（因子、技能、上限、专属、角色限制） | **仓库里的生成器** | 产两类产物：① 可视工具读的数据文件（`Loadout\assets\`，随包、可替换）② 原生的编译表（`.inc`，被 `#include`） |
| 注入状态 / 布局锚点（含 `skill_status` 活表地址锚点）/ 授权 | **原生核心** | C# 只当 ABI 门面 |
| 玩家配置（loadout / 编辑列表） | **可视工具**（唯一写者，也就是唯一校验者） | mod 只做"能否映射成 ABI 结构"的反序列化 |
| 全局热键 | **mod**（它才是常驻进程；反过来会让 mod 依赖"可视工具至少跑过一次"） | 播报给可视工具；可视工具只管"我该不该可见" |
| 跨语言常量 | **一处声明 + 生成 / 断言** | 文档不再承载 |

### 3.2 目标形状

```
游戏 ──解包──> 生成器(仓库内) ──┬─> 可视工具读的数据文件（assets\，随包可替换）
                                └─> 原生的编译表（.inc：注入表 29×3；"gem → 角色"由它派生，不另存）

mod(C# 壳 + C++ 核心) ←── ABI v19（单向）
mod ──读────> 玩家配置（可视工具写的唯一文件）
mod ──播报──> tool-hotkey.txt（反向，一行文本）
```

契约只有**两个半**：**ABI**、**玩家配置**（单向）、**热键播报**（反向一行）。

## 四、四个问题的答案

| 你问的 | 答 |
|---|---|
| **模块、跨语言之间是否联动协调？** | 跨语言契约只有**两个半**（ABI / 玩家配置单向 / 热键反向一行）。ABI 已治理；另两个是**文件协议且无 schema**。协调目前靠人工——一张文档表 + 各处 `keep in sync` 注释，**这本身就是不协调的证据** |
| **数据是否一致？** | 角色限制**一致**（实测：C++ 注入的 87 个 gem 全部能在 gem.json 找到 `character` 行，无 fail-open）。但同一份"87"**有两个来源且集合不同**（3 条 `_74` 只在 gem.json；姬塔只在 C++）→ 存在真实漂移 |
| **是否维护多份类似数据 / 逻辑 / 模块？** | **是**：因子表 ×3 形态 · 专属表 ×2 · 载荷校验 ×4 层 · 跨语言常量 ×20 处人工声明 · `-Check` 门禁 ×2。**这张重复清单就是全部架构缺陷的证据** |
| **当前组织已足够好？** | **分层好，归属没定。**判词：能用但未定 |

## 五、合并后的判据（来自参考技能，去重）

**作用域与方法无关**：diff 级技能的标准可以整条用在项目级（`thermo-nuclear` 就是），反之亦然。

| 判据 | 出处 | 怎么用 |
|---|---|---|
| **deletion test**：删掉它，复杂度是集中了，还是只搬了个地方？ | `codebase-design` · `ponytail-audit` | 判每个候选值不值得做 |
| **the ladder**：① 这层要不要存在？② 既有代码里有吗？③ 标准库？④ 平台特性？⑤ 已装依赖？⑥ 一行？⑦ 最后才写 | `ponytail` | 判每一处新增 / 保留 |
| **边界纪律**：校验、类型收窄、错误处理只放**系统边界**；内部**无条件信任**；业务逻辑是纯函数；壳要薄 | `cursor/plugins@principle-boundary-discipline`（2.5K，Cursor 官方） | **正对着我们最大的病**：它原话是"散落的校验既吵又冗余，还给人**虚假的安全感**" |
| **数概念**：改完之后，读者要同时持有的概念数降了吗？没降就不算更干净；优先让整类分支 / 模式 / 层**消失** | `code-review-and-quality`（架构轴） | 判"这个重构是不是只把复杂度搬了个地方" |
| **8 条不可协商标准 + 6 条推定阻塞项**（>1k 行、ad-hoc 分支、feature 逻辑漏进共享路径、cast/optional churn、边界泄漏、规范 helper 重复） | `thermo-nuclear` | **验收**每条动作后的 diff |
| **一个适配器 = 假设的缝，两个 = 真的缝** | `codebase-design` | 判"这条跨层契约该不该存在" |
| **Design / Deepen / Harden 三模式 + validation loop** | `codebase-architecture`（mblode，225） | 我们是 **Deepen**；每个动作收尾必须有验证回路 |
| **设计树 + 前沿**：只问前置已定的决定，整批一轮问完，**每题附我的推荐答案** | `grilling` | 我出决策、你批的格式 |

**`domain-modeling`：已按它的规矩落地**（2026-09-20）——`CONTEXT.md` 只放词汇、不放实现（值一律指向 `MAINTENANCE §9`），并明确它的边界：只管代码/文档/注释，**可视工具给玩家看的文案除外**（那里沿用游戏的称呼）。两条 ADR 也只收同时满足"难以回退 + 未来读者会困惑 + 真实权衡"三条的决定（`docs/adr/0001`、`0002`）。

## 六、外部约束（不可解构，别把它当自由度）

| 约束 | 谁给的 |
|---|---|
| mod 必须是一个 **.NET 程序集** | Reloaded-II 的 mod 宿主契约 |
| Hook 必须用 **C++ + safetyhook** | 注入本身（C# 做不到） |
| 可视工具必须是**独立进程** | 要在游戏之外有 UI（in-game overlay 是另一个产品决定） |

可以质疑的是**它们之间的分工**（"角色限制表该由谁拥有"就是一个例子），
但把语言差异当内部约定抹掉，就是把宿主约束误判成自由。

### 合并在哪

**合并**：§五 的 8 条判据里，`codebase-design` / `ponytail` / `principle-boundary-discipline` /
`code-review-and-quality` **各贡献一条、不重复出场**；`thermo-nuclear` 与 `ponytail-audit`
只在**验收 / 交叉验证**时出场，不参与设计判断。

### `principle-boundary-discipline` 留下的一个观察项

- 它额外指出一处：**wire 类型经公共表面外露**——ABI 结构（`TemplateSlotNative` /
  `ExclusiveOverrideNative`）由 `LoadoutConfig` **直接构造**，于是"解析配置"与"填 ABI 结构"
  是同一个对象，ABI 一改解析器就得跟着改（原则上该"内部保留 wire 类型，边界只暴露领域概念"）。
- 但**这里没有干净的补救**：分离出领域类型再加一层映射，在本项目会得到一个**零行为的 identity
  映射**——正是 `thermo-nuclear` 判为 thin wrapper 的东西。所以记为**观察项**，不新增待办。
