## 二、判定

**对的部分（别动）**

- 四个单元的划分是**宿主契约**逼出来的：Reloaded-II 要 .NET 程序集、注入要 C++、工具要在游戏之外有界面、界面用 Web。这条分层换来的是"每层只做它非做不可的事"。
- **ABI 是唯一被真正治理过的边界**（版本 + packing + 尺寸断言 + fail-closed）。这说明项目**有能力**把边界定好，只是只定好了一条。
- 两个特性共用一个宿主，而它们只共享 tick / 日志 / 用户目录 = **宿主 + 两个适配器**，不是耦合。可以接受。

**不够好的部分（只有一条，但它是根源）**

> **同一份事实被多个层各自持有，而没有任何一层被指定为它的唯一拥有者。**

这不是"代码乱"，是**所有权缺失**。它所有可观测的复杂度都从这一条长出来：

- 一份因子表存三遍 → 于是需要 `-Check` 门禁、87 行对拍、`assets\` 布局协调、mod 启动 fail-closed 门；
- 一份载荷合法性四层各写一半 → 于是"等级上界"有三份实现，而且 Go 那份校验的不是真正的不变量；
- 一个热键两个进程各自解释 → 于是需要 `tool-hotkey.txt` 这个反向通道；
- 20 个常量靠人工表 → 于是每次改动都要补一行。

**结论：当前组织"能用但未定"。先定归属，简化才有落点**——这正是"架构没定好，怎么简化还是在原地"。

## 三、目标架构：按"谁拥有事实"重新划缝

一句话：**发布物里不放数据文件；每份事实只有一个拥有者；跨层只剩两个半契约。**

### 3.1 所有权表（目标）

| 事实 | 唯一拥有者 | 别人怎么用它 |
|---|---|---|
| 因子 / 词条 / 等级效果的真值 | **游戏** | 谁都不缓存 |
| 表（因子、词条、上限、专属、角色限制） | **仓库里的生成器** | 产两类产物：① 工具的内嵌资产（`go:embed`）② 原生的编译表（`.inc`，被 `#include`） |
| 注入状态 / 布局锚点 / 授权 | **原生核心** | C# 只当 ABI 门面 |
| 玩家配置（loadout / 编辑列表） | **工具**（唯一写者，也就是唯一校验者） | mod 只做"能否映射成 ABI 结构"的反序列化 |
| 全局热键 | **mod**（它才是常驻进程；反过来会让 mod 依赖"工具至少跑过一次"） | 播报给工具；工具只管"我该不该可见" |
| 跨语言常量 | **一处声明 + 生成 / 断言** | 文档不再承载 |

### 3.2 目标形状

```
游戏 ──解包──> 生成器(仓库内) ──┬─> 工具的内嵌资产（go:embed）
                                └─> 原生的编译表（.inc：注入表 29×3 + 限制表 87）

mod(C# 壳 + C++ 核心) ←── ABI v18（单向）
mod ──读────> 玩家配置（工具写的唯一文件）
mod ──播报──> tool-hotkey.txt（反向，一行文本）
```

契约只有**两个半**：**ABI**、**玩家配置**（单向）、**热键播报**（反向一行）。

### A. 让 mod 启动时不再读任何数据文件 【最强】

**现状**：原生 `runtime.cpp` 读 `assets/gem.json` 的 **87 个 `character` 行**做角色限制门——fail-closed，
读不到就**整套 gameplay hook 不装**。C# `LoadoutConfig` 读同一份做词条 cap 与副因子校验。

**为什么是重复真相源**：`kCharacterExclusives[]`（编译进 DLL，29 行 × 3 槽 = **87**）**已经就是那 87 个
专属物品的（角色 → gem）映射**。"哪个 gem 属于哪个角色"这个事实已经有一份**编译期**真相源，
JSON 那份是它的复制品。

**能删掉什么**
- `name_tables.cpp` 的 JSON 扫描与 fail-closed 门
- C# 的 `Sigils` / `Traits` 两张表与等级校验
- `build-release.ps1` 的「87 行」对拍门禁
- mod 对 `gem.json` 的**全部**读取 → 一整类「数据文件缺失/损坏 → 启动失败」路径消失

**收益的性质**：不是"把 fail-closed 做得更好"，而是**把那个门拆掉**。

**已核实（离线，2026-09-19，基准 `24838b1`）**

| 结论 | 证据 |
|---|---|
| **限制查询没有 fail-open** | C++ 注入的 87 个 gem，**全部**能在 gem.json 里找到带非空 `character` 的行（0 缺失）→ 现行为正确，动作 1 不是"修 bug"而是"去重复" |
| `gem.json` 的 87 = **28 角色 × 3** + **3 条 `_74` 进阶** | 带 `character` 的行 87 条、distinct `character` 28 个；其中 3 行 `skill2=6085DA25`（`F1267035`/`C4DD863A`/`43DDE5DD`） |
| C++ 表 87 个 gem、**84 distinct** | 古兰 / 姬塔共用同 3 个 gem（`kGranCharacterHash` ↔ `kDjeetaCharacterHash` 的兼容规则就是为它写的） |
| **两个 87 不是同一个集合** | gem.json 独有那 3 条 `_74`；C++ 独有姬塔（`A4ACBA76`）——它的专属在 gem.json 里记在古兰名下 |

**因此有一处必须修正**：限制表**不能**只从注入表派生（会丢掉那 3 条 `_74` 的限制）。
正确做法是让**生成器同时产出注入表与限制表（87 条）**，一起编进 `.inc`——
即动作 2 的"一种形态"必须把限制数据也纳入，否则动作 1 会静默放宽 3 个物品。

**第二项待核**：等级 cap 校验能否完全交给工具（唯一写者）＋游戏。现在 C# 只提供"更早的报错"，
不提供安全边界——所以这一项是**取舍**而非等价替换，需要在执行前明确。

### D. 仓库自包含

**现状**：生成器在仓库外（`gen/`，父仓库 `.gitignore` 明确忽略），而 `build-release.ps1` 的数据一致性

### 合并在哪 · 顺序在哪

**合并**：§五 的 8 条判据里，`codebase-design` / `ponytail` / `principle-boundary-discipline` /
`code-review-and-quality` **各贡献一条、不重复出场**；`thermo-nuclear` 与 `ponytail-audit`
只在**验收 / 交叉验证**时出场，不参与设计判断。

**顺序**（同一条链，不是并列选项）：

```
1. improve-codebase-architecture 的方法  → §一 现状、§二 判定
2. codebase-design 的词汇与缝判据         → §三 目标架构（缝划在哪）
3. grilling 的格式                        → 把 §六 P0–P6 呈现给你，你批
4. 执行每条：ponytail 的 ladder + principle-boundary-discipline 的边界纪律
5. 每条之后：thermo-nuclear 验收；P3 之后 ponytail-audit 交叉验证
6. domain-modeling                        → 推迟到新架构落地（你的判断）
```

### `principle-boundary-discipline` 对实施计划的影响：**不需要重新计划**

- 它**确认** P4，而不是改变它：P4 本来就是"校验权归一"。
- 它额外指出一处：**wire 类型经公共表面外露**——ABI 结构（`TemplateSlotNative` /
  `ExclusiveOverrideNative`）由 `LoadoutConfig` **直接构造**，于是"解析配置"与"填 ABI 结构"
  是同一个对象，ABI 一改解析器就得跟着改（原则上该"内部保留 wire 类型，边界只暴露领域概念"）。
- 但**这里没有干净的补救**：分离出领域类型再加一层映射，在本项目会得到一个**零行为的 identity
  映射**——正是 `thermo-nuclear` 判为 thin wrapper 的东西。所以记为**观察项**，不新增待办。
- 结论：**§六 P4 的措辞换成它的原话**（校验只在边界做、内部信任、壳保持薄），**顺序与条目不变**。
